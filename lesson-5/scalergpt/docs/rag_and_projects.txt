RAG stands for Retrieval Augmented Generation. It works like an open-book exam for a large language model. Instead of answering only from what it memorised during training, where it may invent facts, the model is given the most relevant passages from your own documents and told to answer using only those passages. The pipeline has three steps: retrieve the relevant chunks, augment the prompt by pasting those chunks into it, and generate the final answer with the language model.

An embedding is a list of numbers that represents the meaning of a piece of text. Texts with similar meanings produce similar lists of numbers, even when they share no words. For example, the phrases "container" and "Docker box" end up close to each other. ScalerGPT uses the OpenAI embedding model called text-embedding-3-small to turn both the document chunks and the user's question into embeddings.

A vector database stores embeddings and can quickly find the stored items that are most similar to a new embedding. ScalerGPT uses ChromaDB running in its own container from the image chromadb/chroma version 0.6.3. The application installs only the thin package called chromadb-client, which talks to the database over HTTP, instead of the full chromadb package, which contains the whole database engine. This keeps the application image small. Because the thin client has no built-in embedding model, an embedding function must be passed explicitly.

Before documents can be searched they must be split into chunks. A whole file is too large and too general to match a specific question, while a single sentence may lack context. A simple and effective strategy is to split each file on blank lines so that every paragraph becomes one chunk. Each chunk is stored with a unique id, such as the file name followed by the paragraph number. Using upsert instead of add means that running the ingestion script twice overwrites existing chunks instead of creating duplicates.

At question time ScalerGPT retrieves the three most similar chunks, joins them into one context block, and sends a system message that tells the model to answer only from that context and to say it does not know when the context does not contain the answer. The user's question goes in the user message. The chat model used is gpt-4o-mini. If the collection is empty, the ask endpoint returns HTTP status 400 with a message explaining that the ingestion script must be run first. Asking a question that is not covered by the documents, such as the capital of France, is a good test that answers are grounded in the documents.

QuickBite ETA is the first project in Lesson 5. It is a food delivery time predictor for a Zomato-style startup. It is trained on five thousand synthetic orders with four features: distance in kilometres, restaurant preparation time in minutes, whether a rider is available, and whether it is raining. The training formula starts from a base of 8 minutes, adds 3 minutes per kilometre, adds 0.7 times the preparation time, adds 9 minutes when it is raining and adds 6 minutes when no rider is available, plus random noise. The model is a RandomForestRegressor with 60 trees, saved as eta_model.pkl with joblib, and served by FastAPI on port 8000 through a POST endpoint called /predict.

ScalerGPT is the second project in Lesson 5. It is a retrieval augmented chatbot built with FastAPI, OpenAI and ChromaDB, run as two containers with Docker Compose. The application container is published on port 8000 and the Chroma container is published on port 8001 of the host while listening on port 8000 internally. The application reads CHROMA_HOST and CHROMA_PORT from environment variables, and it retries the connection to Chroma up to 30 times with a 2 second delay because Chroma takes a few seconds to become ready.

DeskBuddy is the third project in Lesson 5. It is an agentic system with three containers: an agent service that runs the language model and its tool-calling loop, a separate tools service that exposes tools as a microservice, and Redis, which stores conversation memory. The tools service and Redis are not published to the host at all, so they can only be reached from inside the private Compose network. This demonstrates microservice separation and private networking.

The golden rules of Lesson 5 are: rebuild the image after every code change; put rarely changing layers at the top of the Dockerfile; never put secrets in an image; containers talk to each other using service names and internal ports; started does not mean ready, so retry or use healthchecks; containers are disposable while volumes are permanent; and when something breaks, check docker ps -a and then read the logs.
