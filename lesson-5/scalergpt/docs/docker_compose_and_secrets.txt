Docker Compose is a tool for running several containers together from a single file called docker-compose.yml. Instead of typing a separate docker run command for each container, you describe every service once and run docker compose up. If individual docker run commands are like ordering tiffins one at a time, Compose is like ordering a full thali where every dish arrives together. The file is written in YAML, where indentation shows structure. YAML must be indented with spaces and never with tabs.

Each entry under the services key is one container. A service can use build: . to build its image from the Dockerfile in the current folder, or image: to download a ready-made image from Docker Hub, such as chromadb/chroma. The ports key publishes ports, env_file loads environment variables from a file, environment sets individual variables, depends_on controls start order, restart: unless-stopped restarts a crashed container automatically unless a person stopped it on purpose, and volumes mounts persistent storage.

Compose creates a private network for the project, and every service can reach every other service by using its service name as the host name. If the database service is called chroma, the application connects to the host chroma rather than to an IP address or to localhost. Inside a container, localhost means that same container, not your computer and not another container.

There is an important difference between a published port and an internal port. In the mapping 8001:8000, the number 8001 is the port on your computer and 8000 is the port inside the container. Your computer uses the published port, 8001, for debugging. Other containers on the same Compose network are neighbours inside the building, so they must use the internal port, 8000. Setting the application to use port 8001 to reach another container is the single most common bug in multi-container setups and it causes connection refused errors.

The depends_on setting only waits for another container to start, not for the service inside it to be ready. A database container may start in one second but need several more seconds before it accepts connections. If the application connects immediately, it is refused and may exit with an error. There are two fixes. The first is a retry loop in the application that tries to connect, waits two seconds after each failure and tries again up to a limit. The second is a healthcheck on the database service combined with depends_on using condition: service_healthy.

Containers are disposable, but data such as a vector database must survive when a container is removed. A volume is storage managed by Docker that lives outside the container. In Compose, a line such as chroma_data:/chroma/chroma mounts the volume named chroma_data at the folder where Chroma saves its data. The command docker compose down stops and deletes the containers and the network but keeps volumes. The command docker compose down -v also deletes volumes, and that is how data is actually lost.

Useful Compose commands include docker compose up -d --build to rebuild changed images and start everything in the background, docker compose ps -a to list the project's containers including exited ones, docker compose logs app to read one service's logs, and docker compose exec app python ingest.py to run a one-off job inside an already running container. Without the --build flag Compose reuses the old image and code edits do not appear.

Secrets such as API keys must never be written inside a Dockerfile or baked into an image. A helpful rule is that the image is like an ATM card that is safe to share, while the API key is like the PIN, which must be supplied at runtime and never written on the card. If a Dockerfile contains ENV OPENAI_API_KEY=..., anyone with the image can read the key using the docker history command. The correct approach is to keep the key in a .env file, load it with env_file in Compose, and list .env in both .gitignore and .dockerignore. A safe template called .env.example, containing a placeholder value, is committed to Git instead.
