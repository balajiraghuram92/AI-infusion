Docker is a tool that packages an application together with everything it needs to run: the code, the language runtime, system libraries and configuration. This package is called an image. Because the image carries its own environment, the application behaves the same way on a developer laptop, a test server and a cloud machine. Docker exists to solve the classic problem of "but it works on my machine", where code runs for one person and crashes for everyone else because of different Python versions, library versions or operating systems.

A useful analogy is the Mumbai dabbawala tiffin system. The dabbawalas deliver around two hundred thousand lunch boxes every day with very few mistakes because the packaging and the delivery process are standardised. It does not matter what food is inside the tiffin or where it is going. Docker is the dabbawala system for software: the image is the standard tiffin, the container is a tiffin that is out for delivery, Docker Hub is the central kitchen where ready-made tiffins are stored, and a volume is a steel box that comes back after every delivery.

An image is a read-only template, similar to a photograph of a fully prepared computer. A container is a running instance of an image. You can start many containers from the same image and each one is isolated from the others, with its own file system, processes and network. When you edit your source code, the existing image does not change, because the photograph was taken before the edit. To see a code change you must rebuild the image and then start a fresh container from the new image.

A Dockerfile is a plain text file with no extension that contains the recipe for building an image. Docker reads it from top to bottom. FROM chooses the base image, for example python:3.12-slim, which already contains Linux and Python. WORKDIR sets the working folder inside the image, such as /app, and creates it if it does not exist. COPY copies files from your computer into the image. RUN executes a command at build time, such as installing packages with pip. EXPOSE documents which port the application listens on but does not open it. CMD is the single command that runs when a container starts.

Docker builds an image as a stack of layers, one layer per instruction, and it caches each layer. On a rebuild Docker reuses a cached layer if nothing it depends on has changed, but once one layer changes every layer below it must be rebuilt. This is why requirements.txt is copied and installed before the rest of the code is copied. Code changes every day while dependencies change rarely, so placing the slow pip install above the frequently changing code means most rebuilds take seconds instead of minutes. The rule is: rarely changing things at the top, frequently changing things at the bottom.

The docker build command creates an image from a Dockerfile. The -t flag gives the image a name and a version tag in the form name:tag, for example quickbite-eta:v1, and the final dot tells Docker that the Dockerfile and the files to copy are in the current folder. Forgetting the dot is the most common first-day error. If the Dockerfile has a different name, the -f flag points to it.

The docker run command creates and starts a container from an image. The -d flag runs it in the background, known as detached mode. The -p flag maps ports in the form host:container, so -p 8000:8000 forwards traffic from port 8000 on your computer to port 8000 inside the container. The --name flag gives the container a friendly name. Inside the container the web server must listen on host 0.0.0.0, which means accept connections from outside the container. If it listens on 127.0.0.1, port mapping silently fails.

Everyday Docker commands include docker ps to list running containers, docker ps -a to list all containers including ones that have crashed or exited, docker logs -f to stream a container's output, docker exec -it name bash to open a shell inside a running container, docker stop to stop a container and docker rm to remove a stopped container. Removing a container never deletes the image it was created from.

The .dockerignore file lists files and folders that COPY . . must skip, in the same way that .gitignore works for Git. It should exclude Python cache folders, virtual environments that can be hundreds of megabytes, the .git history, secret files such as .env, and any locally trained model files that the image is supposed to create for itself.
